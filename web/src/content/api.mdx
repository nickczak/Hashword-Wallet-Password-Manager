# Hashword API

Account authentication runs inside the same Next.js application as the website. Browser requests use the website's origin; no separate API service is required. Neon stores authentication data. No production base URL is published here.

**Authentication is implemented. Vault storage is planned and its routes below do not exist yet.**

</section>

<section id="authentication">

## Account authentication

Better Auth's browser SDK handles these routes under `/api/auth`:

| Method | Route | Purpose |
| --- | --- | --- |
| POST | `/api/auth/sign-up/email` | Register with name, email, username, and account password |
| POST | `/api/auth/sign-in/username` | Sign in with username and account password |
| GET | `/api/auth/get-session` | Read the current session; returns null when signed out |
| POST | `/api/auth/sign-out` | End the browser session |

The website calls `register`, `login`, `getAccount`, and `logout` from `src/lib/auth-client.ts`. Its account helpers return public `id` and `name` fields; `getAccount` returns null when signed out. Raw Better Auth login/registration responses contain a nested `user` object.

Sessions use HttpOnly browser cookies managed by Better Auth. There is no CLI bearer-token flow or custom `/api/login` route. Registration requires an account password of at least 12 characters. Never send a vault master password to these endpoints. Password-reset and email-verification delivery are not configured in the app.

</section>

<section id="vault-envelope">

## Planned vault format

The Node.js encryption module implements a version-1 envelope with `vaultId`, `ownerId`, Argon2id settings and salt, an encrypted data key, and an encrypted JSON document. AES-256-GCM nonces and authentication tags accompany encrypted values. Binary fields use base64.

Browser encryption and HTTP storage are not connected. A future vault response will include the envelope and a server-managed revision. Clients must decrypt locally and validate the document before displaying it. The backend must derive ownership from the verified session and enforce it on every operation.

</section>

## Planned creation

<Endpoint method="POST" path="/api/vault" />

**Not implemented.** Create the signed-in user's encrypted vault once. Reject attempts to replace an existing vault. The proposed request contains `envelope`; the response contains its ID, envelope, and initial revision. Account creation and vault initialization must be resumable if the initial upload fails.

## Planned retrieval

<Endpoint method="GET" path="/api/vault" />

**Not implemented.** Return only the authenticated owner's encrypted envelope and revision. Decryption happens in the client. An account without a vault should be directed to master-password setup.

<section id="errors">

## Errors

The current auth route returns a generic **503** if backend initialization or request handling throws. Check private environment settings, Neon connectivity, and the auth migration. Better Auth handles credential, validation, session, and rate-limit responses; the browser SDK surfaces their messages.

The following statuses describe the **proposed vault contract**, not existing handlers:

- **400**: invalid encrypted envelope or revision.
- **401**: missing or invalid account session.
- **403**: rejected ownership or request-origin check.
- **404**: no initialized vault.
- **409**: existing vault or conflicting revision.
- **413**: request exceeds the size limit.

</section>
